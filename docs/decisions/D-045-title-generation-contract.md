# D-045: Conversation-title generation contract, and its accepted circuit-breaker shared fate

*Decided: 2026-08-28*

**Context**: Automatic conversation titles ("automatic conversation titles don't work") were broken by a chain of ten defects in `maybeGenerateTitle()` (`dashboard/lib/conversations.ts`) and its call path through `dashboard/lib/llm-context/`: the LAST turn (usually the assistant's own reply) was sent as the "user" question; the persisted title had no length clamp even though `llm-tools/runner.ts`'s `set_title` tool clamps to 100 chars; the whole conversation history was passed through, which could trip `capHistory`'s own extra summarisation LLM call just to produce a ten-word title; `llmComplete`'s provider dispatch had no branch for `e2e-stub`, so any caller other than the one place `turn-background.ts` short-circuits for it (the main turn) fell through into the OpenRouter branch and threw an unrelated "no API key" error; and the failure was swallowed by a bare `catch {}` with no logging, making it invisible to the operator. Two adjacent, related defects in the same conversation/LLM-context layer were fixed in the same PR: two independent, drift-prone implementations of the free-chat system prompt (`lib/conversation-context.ts` and `lib/llm-context/system-prompt.ts` each had their own byte-identical copy), and an unrecognised `conversation.mode` (specifically `"summary"`, the real, live "✦ Resumen semanal" flow) silently getting an empty system prompt and no tools while still being billed for a real LLM call.

**Decision**:
1. **Title source**: a title is generated from the FIRST user message in the conversation (what the conversation is ABOUT), never the most recent turn. At most the first assistant reply rides along as one prior-turn message, truncated to 300 chars, purely as extra context — this also caps history at 1 message by construction, so `capHistory` can never fire its own extra summarisation call for a title request.
2. **Length**: the persisted title is always clamped to 100 chars (`title.trim().replace(/^["']|["']$/g, "").slice(0, 100)`), matching the `set_title` tool handler's own clamp — required because the CLI provider silently ignores `maxOutputTokens` (no such flag exists on the CLI binary; not something we can fix from the dashboard side) and any provider's model can ignore prompt instructions regardless.
3. **e2e-stub boundary**: `llmComplete()` (`lib/llm-client.ts`) now has an explicit `"e2e-stub"` branch that throws a typed `E2eStubProviderError` instead of silently falling through to the OpenRouter branch — `LlmResponse.provider`'s type already excluded `"e2e-stub"`, so the runtime now matches that contract. `maybeGenerateTitle()` additionally skips early under `DASHBOARD_LLM_PROVIDER=e2e-stub`, mirroring `turn-background.ts`'s own short-circuit for the main turn, so this is fixed at the boundary (protecting every future caller) AND at this specific call site (avoiding a pointless boundary error on every conversation's first turn in e2e-stub mode).
4. **Failure visibility**: a title-generation failure is logged (`console.warn`, with `conversationId`, `flow=title`, `provider`, and the error message passed through `lib/llm-provider/sanitize.ts` per D-024) but never thrown — the outer `.catch(() => {})` at the call site in `turn-background.ts` keeps swallowing it so a title failure can never fail a turn. Titles stay cosmetic to the user (the UI falls back to `first_user_prompt`), but the failure is no longer invisible to the operator.
5. **Dead code removed**: `POST /api/conversations/:id/generate-title` had zero client callers and is deleted rather than kept "just in case" (AGENTS.md § Backwards compatibility — default is to break it).
6. **Flow-name exhaustiveness**: `lib/llm-context/types.ts` gains `LLM_FLOWS` (a const tuple of every flow name `buildSystemPrompt()`/`toolsForFlow()` handle) and `isLlmFlow()` (a type guard narrowing a raw string to that union). `buildSystemPrompt()`'s dispatch switch is exhaustive over this union via a `default: { const _exhaustive: never = flow; ... }` check — adding a flow to `LLM_FLOWS` without a matching `case` fails to compile. `turn-background.ts`'s `runGenericTurn()` calls `isLlmFlow()` before `assembleRequest()` as belt-and-braces (a `console.warn` on an unrecognised `conversation.mode`) — this is NOT the fix (the fix is the compile-time exhaustiveness above), it is pure observability so a bad flow name shows up in logs instead of silently producing a low-quality but billed reply.
7. **`"summary"` flow got a real prompt, not removed from `VALID_MODES`**: the exhaustiveness check in (6) forced a choice between adding a real case for `"summary"` or removing it from `VALID_MODES` (`app/api/conversations/route.ts`). `"summary"` is a real, live, user-reachable mode — `WeeklySummaryButton.tsx` ("✦ Resumen semanal") creates a conversation with `mode: "summary"`, seeded with a prompt (`lib/seed-prompts.ts`) that explicitly asks the model to call `validate_query` / `execute_query` / `list_ps_tables` / `describe_ps_table`. Before this fix, `buildSystemPrompt("summary", …)` fell through the default branch to an empty prompt AND `toolsForFlow("summary")` returned `[]` — every weekly-summary conversation sent a real, billed LLM call that could not do what its own seed prompt asked. The fix gives `"summary"` its own preamble (`SUMMARY_PREAMBLE`, distinct text from `"chat"`'s) and the same `FREE_CHAT_TOOLS` catalog as `"chat"` (`toolsForFlow`) — this is a deliberate, reviewable, single named case in the exhaustive switch, not a runtime fallback for any unrecognised mode onto `"chat"`'s tool grant (which point 6 explicitly avoids). Note: `lib/llm.ts`'s `generateSuggestions()` (verified dead code — zero callers anywhere in the app) also passes `flow: "summary"` to `assembleRequest()` as an unrelated internal sentinel for "no system prompt, no tools"; since it is unreachable, giving `"summary"` real content does not change any live behaviour, but the naming collision is worth knowing about if that function is ever revived.
8. **Duplicate free-chat prompt removed**: `lib/conversation-context.ts`'s `buildFreeChatContext()` (feeds the UI's "Contexto original" panel) now delegates to `buildSystemPrompt("chat", {})` / `toolsForFlow("chat")` from `@/lib/llm-context` (the single LLM entry point, D-036) instead of carrying its own byte-identical copy of the preamble and knowledge assembly. This also exposed and fixed a latent bug in `llm-context/system-prompt.ts`'s own `buildFreeChatContext()`: it looked up `FREE_CHAT_TOOLS` via a runtime `require("@/lib/llm-tools/catalog")` instead of a static import, which failed to resolve the `@/` path alias outside certain execution contexts (surfaced by `prompt-snapshots.test.ts` once this file became the second real caller of that code path) — replaced with a plain static import.
9. **Circuit-breaker shared fate: accepted, not fixed**. The title call runs through `callWithCircuitBreaker` — the SAME breaker that protects `generate`/`chat`/`modify`/`analyze`. A cosmetic, single-question call can therefore contribute failures to the breaker guarding product flows. This is a DELIBERATE, RECORDED choice, not an oversight: the breaker protects the underlying PROVIDER, not a specific flow, and a provider that cannot produce a ten-word title is genuinely down for everything else too. Fixing defect #4 above (the e2e-stub fall-through) removes the one known always-throwing case that could previously trip the breaker for a reason unrelated to the provider's real health; the remaining shared fate is accepted.

**Alternatives rejected**:
- Falling back to `"chat"`'s system prompt/tools at RUNTIME for any unrecognised flow (what the sibling forks that inspired this fix originally did for `"summary"`). Rejected: it silently grants an unknown mode `"chat"`'s full 12-tool catalog (including `start_dashboard_generation`) — a silent capability escalation. The chosen fix instead makes the switch exhaustive at compile time and gives `"summary"` its own deliberate, reviewed case.
- Giving `maybeGenerateTitle()` its own private circuit breaker, separate from the flows it shares a provider with. Rejected as unnecessary complexity — see point 9.
- Adding a CLI `--max-tokens`-equivalent flag. Rejected: no such flag exists on the `claude` CLI; the length clamp (point 2) makes the missing enforcement harmless regardless of provider.

**Rationale**: Every change here narrows a previously silent failure mode (empty prompt, wrong message, unbounded history, an unhandled provider branch, a swallowed error, a dead route, a duplicated prompt, an unlisted flow) into either a compile-time check, a bounded/clamped value, or a logged diagnostic — without changing user-visible behaviour beyond "titles now actually appear."
